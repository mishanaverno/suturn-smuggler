# Задача: прогноз траектории через границы сфер влияния

Репозиторий: `github.com/mishanaverno/suturn-smuggler`
Базовая ветка: `main`, **после** задачи про данные системы Сатурна (`TASK-saturn-system-data.md`)
Unity 6000.2.0f1, тесты — Unity Test Framework (NUnit), сборка `Assets/Tests/Game.Tests.asmdef`
(EditMode)

## Контекст и зачем это нужно

Переходы между сферами влияния уже работают, но это **реакция**: корабль пересёк границу —
код переподчинил его новому телу. Игрок при этом летит вслепую. Чтобы попасть с орбиты
Титана на орбиту Реи, он должен видеть заранее: если сжечь вот столько и вот в эту сторону,
то через столько-то суток траектория войдёт в сферу влияния Реи вот в этой точке и с вот
такой относительной скоростью.

Это и есть предмет задачи: по начальному состоянию построить последовательность конических
дуг, разделённых пересечениями границ SOI, и отдать её на отрисовку.

Ключевое требование: прогноз должен считаться **от гипотетического состояния**, а не только
от текущего. Игрок крутит `deltaLVLHVelocity` у манёвра и хочет видеть, куда приведёт
получившаяся орбита — значит вход у функции это элементы орбиты и центральное тело, а не
`playerShip`.

Точки входа:

- `Assets/Scripts/Space/Sim/AstroDynamic.cs` — распространение орбиты, трогать не нужно;
- `Assets/Scripts/Space/Sim/SOITransition.cs` — рантайм-переходы, рядом с ними и место новому коду;
- `Assets/Scripts/Space/Sim/Maneuver.cs` — `newOrbitParams`, от которых считается прогноз;
- `Assets/Scripts/Space/Sim/OrbitRenderer.cs` — сейчас рисует одну орбиту, надо научить рисовать цепочку.

## Что построить

### 1. Модель результата

```csharp
public sealed class TrajectoryPatch
{
    public SpaceObject Central;        // тело, вокруг которого идёт эта дуга
    public OrbitElements Orbit;        // коника относительно него
    public double StartEpoch;          // когда дуга начинается
    public double EndEpoch;            // когда заканчивается (или горизонт, если событий нет)
    public PatchEndReason EndReason;   // Entered / Escaped / Horizon / Impact
    public SpaceObject NextCentral;    // куда переходим, null если дуга последняя
}

public enum PatchEndReason { Horizon, EnteredSOI, EscapedSOI, Impact }
```

Прогноз — это `IReadOnlyList<TrajectoryPatch>`.

### 2. Класс прогноза — без Unity

Новый файл, например `Assets/Scripts/Space/Sim/TrajectoryPredictor.cs`. Никаких обращений
к `GameMono.instance`, `Time` или `MonoBehaviour`: время и состояние передаются параметрами.
Это не стилистика — прогноз по своей природе считает состояние на сотни моментов вперёд, и
через синглтон текущего времени он работать не может в принципе. Плюс только так его можно
проверить тестом, а проверять тут есть что.

Примерная сигнатура:

```csharp
public static List<TrajectoryPatch> Predict(
    OrbitElements startOrbit,
    SpaceObject startCentral,
    double startEpoch,
    double horizon,          // на сколько секунд вперёд смотреть
    IReadOnlyList<SpaceObject> bodies,
    PredictSettings settings);
```

### 3. Алгоритм по одной дуге

В пределах одной дуги корабль движется по конике вокруг `Central`. Ищутся два типа событий,
берётся ближайшее по времени:

**Выход из сферы влияния `Central`.** Корень уравнения `|r(t)| = SOI_Central`. Функция
`|r(t)|` на конике ведёт себя просто: у эллипса колеблется между перицентром и апоцентром,
у гиперболы монотонно растёт после перицентра. Если апоцентр эллипса меньше `SOI_Central` —
события нет вообще, проверяется без всякого поиска. У корня системы (Сатурна) SOI бесконечен,
выхода нет.

**Вход в сферу влияния дочернего тела `C`.** Корень уравнения

```
f(t) = |r_корабля(t) − r_C(t)| − SOI_C = 0
```

Обе позиции аналитические, так что `f` вычисляется прямо, но она колебательная и корней у
неё может быть много — нужен первый.

**Столкновение** — `|r(t)| < radius_Central`. Отдельным событием, чтобы прогноз не рисовал
траекторию сквозь луну.

На найденном событии: посчитать состояние корабля и нового центрального тела на момент
события, взять разность, построить новые элементы через
`AstroDynamic.CalculateOrbitElements` с `mu` нового тела и эпохой события — и продолжить
с новой дуги. Ровно та же операция, что делает `SOITransition.ChangeCentralBody` в рантайме;
имеет смысл вынести общую часть, чтобы прогноз и симуляция не разъехались.

### 4. Шаг поиска — здесь главная ловушка

Наивное решение — равномерная сетка по времени с уточнением бисекцией на интервале, где `f`
сменила знак. Оно молча не работает.

Проверено численно на перелёте с орбиты Титана к Рее (встречный курс, горизонт 30 суток,
SOI Реи 3676 км):

| шаг сетки | результат | вычислений |
|-----------|-----------|------------|
| 3600 с | **встреча не найдена вообще** | 1442 |
| 600 с | вход в t = 416986.4 с | 1416 |
| 60 с | вход в t = 416986.2 с | 13918 |
| адаптивный | вход в t = 416986.4 с | **244** |

При шаге в час корабль перепрыгивает сферу влияния Реи насквозь между двумя отсчётами, и
функция ни разу не становится отрицательной. Прогноз не падает и не ругается — он сообщает,
что встречи нет. Это худший вид ошибки: игрок целится в Рею, прогноз говорит «промах»,
игрок правит манёвр и промахивается по-настоящему.

Ширина окна пролёта равна примерно `2·SOI / v_отн`. Для системы Сатурна при относительной
скорости порядка орбитальной:

| луна | SOI, км | окно |
|------|---------|------|
| Mimas | 250 | ~0.6 мин |
| Enceladus | 489 | ~1.3 мин |
| Tethys | 1214 | ~3.6 мин |
| Dione | 1955 | ~6.5 мин |
| Rhea | 3676 | ~14 мин |
| Titan | 43322 | ~4.3 часа |
| Hyperion | 926 | ~6 мин |
| Iapetus | 22515 | ~3.8 часа |
| Phoebe | 9498 | ~3.1 часа |

Равномерная сетка, безопасная для Мимаса, — это шаг порядка 20 секунд, то есть 130 тысяч
отсчётов на тридцать суток горизонта **на каждое тело**. Неприемлемо.

**Требуемое решение — адаптивный шаг по расстоянию.** Следующий шаг выбирается так, чтобы
за него объекты физически не успели сблизиться на текущее расстояние:

```
dt = clamp(currentGap / vMax, minStep, maxStep)
```

где `currentGap` — текущее значение `f(t)` (расстояние до границы сферы), а `vMax` —
**гарантированная верхняя оценка скорости сближения**. Здесь нельзя ошибиться в меньшую
сторону: заниженная оценка возвращает ту же пропущенную встречу. Безопасная оценка —
сумма максимальной скорости корабля на его конике (по vis-viva в перицентре) и максимальной
скорости тела на его орбите.

В прототипе это дало 244 вычисления против 13918 у равномерной сетки с шагом 60 с — при
одинаковом ответе с точностью до долей секунды.

**Предфильтр по геометрии.** До всякого поиска отбросить тела, до которых коника не достаёт:
если перицентр корабля больше апоцентра тела плюс его SOI, или апоцентр корабля меньше
перицентра тела минус SOI — встречи быть не может. Для замкнутых орбит это отсекает почти
все тела за несколько арифметических операций.

**Уточнение корня** — бисекция на интервале со сменой знака, до точности порядка секунды.
Ньютон здесь не нужен и вреден: производная `f` дорогая, а рядом с касательным сближением
функция ведёт себя плохо.

**Касательные сближения.** Если `f` опускается ниже нуля и возвращается внутри одного шага,
смены знака на концах не будет. Адаптивный шаг делает это маловероятным, но для надёжности
стоит отслеживать не только знак на концах, но и то, что расстояние начало расти после
убывания — при смене направления имеет смысл проверить минимум внутри интервала.

### 5. Выбор цели и точка наибольшего сближения

**Это второй этап, отделяемый от остального.** Пункты 1–4 и 6–8 самодостаточны: прогноз
через границы сфер влияния работает и без выбора цели. Если задача берётся в один заход —
делать после того, как заработает и будет покрыт тестами прогноз по SOI. Раздел описан
здесь, чтобы решения по структуре принимались сразу с оглядкой на него: развёртка по
времени и кеш у обоих режимов общие, и переделывать их потом не придётся.

Станции — единственные порты, но не единственные объекты, к которым корабль подходит:
закладка на парковочной орбите, обломок, встреча с другим кораблём. У таких целей нет
ни массы, ни сферы влияния, поэтому событие «пересёк границу» к ним неприменимо. Нужен
второй режим, как выбор цели в KSP: игрок назначает объект целью и видит **точку
наибольшего сближения**.

Отличие от поиска пересечения SOI принципиальное: там ищется корень функции расстояния,
здесь — её **минимум**. Ответ тоже другой и состоит из трёх чисел, без которых до цели не
долететь: момент сближения, расстояние в этот момент и относительная скорость в этот момент.

**Общая система отсчёта.** Корабль и цель могут вращаться вокруг разных тел (корабль вокруг
Сатурна, станция вокруг Реи), поэтому расстояние считается в абсолютных координатах: позиция
собирается сложением по цепочке родителей. Для корабля на момент `t` берётся та дуга
прогноза, которая этот момент покрывает, — то есть сближение ищется по всей предсказанной
траектории, включая участки после смены центрального тела.

**Алгоритм.** Тот же адаптивный проход по времени, что и для SOI: шаг `dt = clamp(d / vMax,
minStep, maxStep)`, где `d` — текущее расстояние до цели. Локальный минимум брекетится по
трём последовательным отсчётам (`d1 < d0 && d1 <= d2`) и уточняется золотым сечением или
параболической интерполяцией на этом интервале. Бисекция здесь не подходит: ищется минимум,
а не корень.

Проверено численно на перелёте с орбиты Титана к станции на орбите радиуса Реи, с намеренным
промахом по фазе (горизонт — полтора полуэллипса, около 6.3 суток):

| метод | момент | расстояние | вычислений |
|-------|--------|------------|------------|
| равномерная сетка, 2 млн отсчётов | 418549.76 с | 50.539 км | 2 000 001 |
| адаптивный проход + золотое сечение | 418549.68 с | 50.539 км | **340** |

Расхождение — 0.08 с по времени и 0.2 м по расстоянию. Результат не зависит от `maxStep`:
при значениях 600, 1800, 3600 и 7200 с момент и расстояние совпадают до последнего знака,
меняется только число вычислений (1048 / 472 / 339 / 280).

**Что возвращать.** Список ближайших сближений (двух-трёх достаточно), каждое —
момент, расстояние, относительная скорость. Плюс позиции корабля и цели в этот момент:
именно две метки, соединённые линией, делают картинку читаемой — как в KSP.

**Вырожденные случаи, которые нужно обработать явно:**

- цель — то самое тело, вокруг которого корабль сейчас летит: минимум расстояния это просто
  перицентр, отдельного смысла не имеет;
- цель на почти той же орбите (соорбитальная): расстояние почти постоянно, минимум размазан
  и численно неустойчив — не выдавать мусор, а сообщать, что сближения нет;
- траектория обрывается раньше горизонта (столкновение или лимит дуг) — искать только внутри
  предсказанного интервала;
- минимумов много и все мелкие — ограничить число возвращаемых.

### 6. Ограничения и настройки

`PredictSettings` с полями: горизонт по времени, максимальное число дуг (4–5 достаточно),
`minStep` / `maxStep`, точность уточнения корня. Всё — с внятными значениями по умолчанию
в одном месте, а не константами по коду.

Прогноз обрывается по любому из условий: горизонт, лимит дуг, столкновение.

### 7. Когда пересчитывать

Прогноз не должен считаться каждый кадр. Пересчёт нужен, когда меняется вход: элементы
орбиты корабля, `deltaLVLHVelocity` манёвра, `startEpoch` манёвра, центральное тело.
Простейшее решение — флаг «протух», выставляемый в этих местах, и пересчёт не чаще одного
раза за N кадров. Результат кешируется.

### 8. Отрисовка

`OrbitRenderer` сейчас рисует одну орбиту вокруг одного центра. Научить его рисовать цепочку
дуг: каждая дуга рисуется в своей системе отсчёта, но переводится в глобальные координаты,
чтобы линия была непрерывной. Дуги полезно различать визуально — хотя бы цветом или яркостью,
чтобы игрок видел, где траектория меняет хозяина.

Отдельно пометить точку входа в SOI и, если она есть, точку столкновения.

Для выбранной цели — две метки в точке наибольшего сближения (положение корабля и положение
цели на этот момент), соединённые линией, и подпись с тремя числами: через сколько,
на каком расстоянии, с какой относительной скоростью.

## Тесты

Главный тест здесь один, и он ценнее всех остальных вместе взятых.

1. **Прогноз согласован с симуляцией.** Построить прогноз от некоторого состояния, затем
   прогнать `SimWorld` вперёд обычным ходом времени и проверить, что корабль действительно
   сменил центральное тело в предсказанный момент (с точностью до пары секунд) и в
   предсказанной точке (с относительной точностью 1e-6). Это единственная проверка, которая
   ловит рассогласование между тем, что игрок видит, и тем, что произойдёт, — а именно оно
   здесь и есть главный риск. Прогнать в обе стороны: и для входа в SOI, и для выхода.

2. **Пропущенная встреча.** Тот самый случай из таблицы: перелёт, при котором равномерная
   сетка с часовым шагом встречу теряет. Прогноз обязан её найти. Это регрессионный тест
   ровно на ошибку, из-за которой писался пункт про адаптивный шаг.

3. **Устойчивость к настройкам.** Один и тот же перелёт при `maxStep`, отличающемся в
   десять раз, даёт одинаковый момент входа с точностью до секунды. Если результат зависит
   от шага — оценка `vMax` неверна.

4. **Встречи нет.** Круговая орбита вокруг Сатурна между орбитами двух лун, не касающаяся ни
   одной сферы влияния: прогноз возвращает одну дугу с `EndReason == Horizon`.

5. **Выход из SOI.** Гиперболическая траектория от Титана: момент выхода совпадает с
   аналитическим решением `|r(t)| = SOI` с точностью до секунды.

6. **Столкновение.** Траектория с перицентром внутри радиуса луны обрывается с
   `EndReason == Impact`, а не рисуется сквозь тело.

7. **Детерминизм.** Один и тот же вход даёт побитово одинаковый результат.

8. **Прогноз от манёвра.** Прогноз, построенный от `Maneuver.newOrbitParams`, совпадает с
   тем, что произойдёт, если этот манёвр действительно исполнить.

9. **Сближение совпадает с эталоном.** Для перелёта с известной геометрией найденный момент
   наибольшего сближения совпадает с результатом очень мелкой равномерной сетки: по времени
   не хуже секунды, по расстоянию не хуже метра. Проверено на прототипе — расхождение
   получилось 0.08 с и 0.2 м.

10. **Сближение не зависит от `maxStep`.** Тот же перелёт при `maxStep` 600, 1800, 3600 и
    7200 с даёт один и тот же момент и одно и то же расстояние. Если результат поехал —
    оценка `vMax` занижена.

11. **Сближение согласовано с симуляцией.** Прогнать `SimWorld` вперёд и убедиться, что
    фактическое минимальное расстояние до цели достигается в предсказанный момент и равно
    предсказанному.

12. **Цель за границей SOI.** Корабль вокруг Сатурна, цель на орбите вокруг луны: сближение
    считается верно, то есть абсолютные координаты собираются по цепочке родителей, а не
    сравниваются относительные.

13. **Соорбитальная цель.** Цель на почти той же орбите: функция не выдаёт случайный минимум,
    а сообщает об отсутствии осмысленного сближения.

14. **Предфильтр ничего не теряет.** На наборе случайных орбит результат с включённым и
   выключенным предфильтром одинаков. Фильтр — оптимизация, и он обязан быть консервативным.

## Критерий приёмки

- Все существующие тесты зелёные.
- В сцене можно задать манёвр, покрутить `deltaLVLHVelocity` и видеть, как предсказанная
  траектория уходит в сферу влияния другой луны.
- Можно назначить объект целью и, правя манёвр, сводить расстояние в точке наибольшего
  сближения к нужному — то есть прицеливаться в рандеву, а не только в сферу влияния.
- Предсказанный момент входа совпадает с фактическим, когда время до него доходит.
- Пересчёт прогноза не роняет частоту кадров: на перелёте через всю систему укладывается
  в единицы тысяч вычислений положения, а не в сотни тысяч.

## Отдельно, НЕ входит в эту задачу

1. **Автоматический подбор манёвра** (решение задачи Ламберта, поиск окна запуска). Игрок
   целится руками — этого достаточно для первой версии, и без ручного прицеливания непонятно,
   каким должен быть автомат.
2. **Возмущения.** Прогноз, как и симуляция, остаётся патчед-кониками: ни притяжения третьих
   тел, ни сплюснутости Сатурна. Это осознанное упрощение, но стоит помнить, что реальная
   траектория будет отклоняться, и коррекции по пути — это игровая механика, а не баг.
3. **Конечная тяга в прогнозе.** Прогноз строится от импульсного манёвра. Длинный прожиг
   даёт отклонение, которое игрок гасит по ходу — это часть управления кораблём, а не задача
   прогноза.
4. **Два режима отображения.** Цепочка дуг длиной в миллиард метров и корабль длиной сто
   метров в одной сцене по-прежнему не помещаются.

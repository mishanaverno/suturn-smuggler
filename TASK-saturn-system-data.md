# Задача: реальная система Сатурна и загрузка мира из файла данных

Репозиторий: `github.com/mishanaverno/suturn-smuggler`
Базовая ветка: `main`, **после** задачи про скорость и переходы между сферами влияния
(`TASK-soi-transitions.md`) — она меняет те же места в `SimMono` и `SpaceObject`.
Unity 6000.2.0f1, тесты — Unity Test Framework (NUnit), сборка `Assets/Tests/Game.Tests.asmdef`

## Контекст и зачем это нужно

Игра целиком происходит внутри системы спутников Сатурна: игрок возит грузы между лунами.
Но мир сейчас собирается в `GameMono.LoadGame` прямо в C# из выдуманных Солнца, Земли и
Луны с круглыми числами вроде `mass = 19000000000 * Constants.simMassMultiplier`.

Пока карта выдуманная, ничего нельзя спроектировать: неизвестны времена перелётов, бюджеты
характеристической скорости, сколько игровых суток занимает рейс, сколько нужно топлива и
припасов. Это входные данные для всей экономики и структуры миссий. Задача — заменить
выдуманную систему на настоящую и вынести её из кода в файл данных.

Точки входа:

- `Assets/Scripts/Game/GameData.cs` — классы `GameData`, `SystemData`, `ObjectData`, `PlayerShip`;
- `Assets/Scripts/Game/GameMono.cs`, метод `LoadGame` — здесь сейчас захардкожен мир;
- `Assets/Scripts/Space/Sim/SimMono.cs`, метод `CreateSim` — строит объекты по данным;
- `Assets/Scripts/Utilities/ResourcesLoader.cs` — загрузка префабов из `Resources/Prefabs`.

## Решение 1. Корнем системы становится Сатурн, а не звезда

Сейчас `SimMono` требует объект `star` и вешает всё остальное на него. Предлагается сделать
корнем **Сатурн**, а Солнце не моделировать как тело симуляции вообще.

Обоснование: вся игра происходит внутри системы Сатурна, гелиоцентрическая орбита самого
Сатурна за 29 лет не даёт игроку ничего наблюдаемого, зато поднимает все координаты на два
порядка (1.4·10¹² м вместо 10⁹) и ухудшает и без того напряжённый масштаб отображения.

Солнце понадобится позже для тепловой механики — как направление освещения и источник
потока, а также чтобы считать тень луны. Для этого достаточно хранить направление на Солнце
и расстояние до него как параметры системы, а не как тело на орбите. Заложить это поле в
формат данных сразу, использовать позже.

Практически: переименовать `SystemData.star` в `root` (или `centralBody`), убрать
предположение «корень — это звезда». Признак `SpaceObject.IsStar` сейчас означает «нет
родителя» — переименовать в `IsRoot`, семантика не меняется.

## Решение 2. В данных хранится GM, а не масса

Сейчас `SpaceObject` принимает `mass` и считает `MU = Constants.realG * mass`.

Для реальных тел это хуже во всех отношениях. Гравитационная постоянная G известна с
относительной точностью около 2·10⁻⁵ — это худшая по точности из всех фундаментальных
констант. А произведение GM для тел Солнечной системы измерено напрямую по движению
аппаратов с точностью до 10⁻⁹ и лучше. Перемножая неточную G на массу, полученную делением
измеренного GM на ту же неточную G, вы теряете пять порядков точности на ровном месте.

Поэтому: в файле данных хранить **GM в м³/с²**, а `mass` не хранить вообще.

Проверка, что масса нигде больше не нужна: единственное место — расчёт сферы влияния
`SOI = a · (m / M)^(2/5)`. Отношение масс равно отношению GM, поэтому формула переписывается
как `SOI = a · (GM_тела / GM_центрального)^(2/5)` и масса исчезает. Убедиться, что после
правки поле `mass` не осталось нигде, кроме, возможно, корабля, где масса нужна по-настоящему
(для расчёта тяги) и задаётся отдельно в килограммах.

## Решение 3. Тела задаются элементами орбиты, а не вектором состояния

Сейчас `ObjectData` содержит `position` и `velocity`, а орбита выводится из них в
`SetVelocity`. Но справочные данные по спутникам публикуются именно как кеплеровы элементы,
и подгонять под них вектор состояния вручную — лишний шаг с потерей точности.

Новый формат объекта:

- `id` — строковый идентификатор, уникальный;
- `name`, `description` — для интерфейса;
- `parent` — `id` центрального тела; у корня пусто;
- `gm` — гравитационный параметр, м³/с²;
- `radius` — средний радиус тела, м;
- `orbit` — элементы: `semiMajorAxis` (м), `eccentricity`, `inclination` (град),
  `longitudeOfAscendingNode` (град), `argumentOfPeriapsis` (град), `meanAnomalyAtEpoch` (град
  в файле, радианы внутри — конвертировать при загрузке), `epoch` (секунды от начала отсчёта
  игры); у корня отсутствует;
- `simPrefab` — имя префаба.

Иерархия задаётся полем `parent` явно. Убрать из `SimMono.CreateSim` определение
центрального тела перебором «расстояние меньше SOI»: для статических тел это лишняя
эвристика, которая при близких лунах может ошибиться. Динамическое определение остаётся
только для корабля и только в рантайме (это предмет предыдущей задачи).

Порядок создания: тела создавать в порядке обхода иерархии от корня вниз, а не по убыванию
массы. Родитель обязан существовать раньше ребёнка. Отсутствие родителя, цикл в иерархии
или несколько корней — ошибка загрузки с внятным сообщением, а не молчаливое падение.

## Решение 4. Файл данных

Формат — JSON, размещение — `Assets/StreamingAssets/systems/saturn.json` либо
`Assets/Resources/Data/saturn.json` (на усмотрение; `StreamingAssets` предпочтительнее,
потому что файл можно править без пересборки).

`GameMono.LoadGame` вместо конструирования объектов читает и разбирает этот файл.
`JsonUtility` не умеет `double` в некоторых случаях и не умеет вложенные списки объектов
надёжно — использовать `Newtonsoft.Json` (пакет `com.unity.nuget.newtonsoft-json`) либо
написать разбор вручную. Не терять точность: числа разбирать как `double` с
`CultureInfo.InvariantCulture`.

## Данные системы Сатурна

Источник: NASA JPL Solar System Dynamics, эфемерида **SAT441** (Jacobson, 2022).
Физические параметры — `ssd.jpl.nasa.gov/sats/phys_par/`, средние элементы орбит —
`ssd.jpl.nasa.gov/sats/elem/sep.html`. Параметры Сатурна — `ssd.jpl.nasa.gov/planets/phys_par.html`.

**Центральное тело**

| Тело   | GM, м³/с²   | Средний радиус, м | Экваториальный радиус, м |
|--------|-------------|-------------------|--------------------------|
| Сатурн | 3.7931206e16 | 5.8232e7          | 6.0268e7                 |

**Спутники.** GM переведён из км³/с² умножением на 1e9, радиусы и большие полуоси — из км
умножением на 1e3. Углы в градусах. Эпоха элементов: 2000-01-01.5 TDB (J2000).

| Спутник   | GM, м³/с²    | Радиус, м | a, м       | e     | i, град | ω, град | Ω, град | M, град |
|-----------|--------------|-----------|------------|-------|---------|---------|---------|---------|
| Mimas     | 2.50349e9    | 1.9820e5  | 1.86000e8  | 0.020 | 1.6     | 160.4   | 66.2    | 275.3   |
| Enceladus | 7.21037e9    | 2.5210e5  | 2.38400e8  | 0.005 | 0.0     | 119.5   | 0.0     | 57.0    |
| Tethys    | 4.121353e10  | 5.3110e5  | 2.95000e8  | 0.001 | 1.1     | 335.3   | 273.0   | 0.0     |
| Dione     | 7.311607e10  | 5.6140e5  | 3.77700e8  | 0.002 | 0.0     | 116.0   | 0.0     | 212.0   |
| Rhea      | 1.5394175e11 | 7.6350e5  | 5.27200e8  | 0.001 | 0.3     | 44.3    | 133.7   | 31.5    |
| Titan     | 8.9781371e12 | 2.5747e6  | 1.22190e9  | 0.029 | 0.3     | 78.3    | 78.6    | 11.7    |
| Hyperion  | 3.7049e8     | 1.3500e5  | 1.48150e9  | 0.105 | 0.6     | 214.0   | 87.1    | 122.9   |
| Iapetus   | 1.2051511e11 | 7.3430e5  | 3.56170e9  | 0.028 | 7.6     | 254.5   | 86.5    | 74.8    |
| Phoebe    | 5.5479e8     | 1.0650e5  | 1.292940e10| 0.164 | 175.2   | 240.3   | 192.7   | 308.0   |

**Важная оговорка про плоскость отсчёта.** JPL публикует эти средние элементы относительно
**локальных плоскостей Лапласа**, своих для каждого спутника, а не относительно одной общей
плоскости. Для ближних лун (от Мимаса до Реи) плоскость Лапласа практически совпадает с
экваториальной плоскостью Сатурна, и наклонения из таблицы можно брать как есть. Для Япета
(i = 7.6°) и особенно Фебы (i = 175.2°, ретроградная) это уже не так: их углы Ω и ω заданы в
другой системе отсчёта, и подстановка их в общую плоскость даст неверную ориентацию орбиты.

Как поступить: для первой версии считать все элементы заданными в экваториальной плоскости
Сатурна, но **написать это в комментарии в файле данных**, чтобы позже никто не принял
результат за настоящую эфемериду. Для Фебы сохранить ретроградность (i > 90°) — она важна
как игровой факт: туда лететь дорого. Точная привязка к плоскостям Лапласа — отдельная
задача, если и когда понадобится.

**Что не брать.** Мелкие спутники (Янус, Эпиметей, Прометей, Пандора, троянцы) и кольца в
этой задаче не нужны. Кольца потребуют отдельной модели — они не тело и не орбита.

**Корабль игрока.** Задать на низкой орбите вокруг Титана: `parent: "titan"`, круговая
орбита радиусом порядка `2.9e6` м (около 350 км над поверхностью), `e = 0`, `i = 0`.
Массу корабля задать отдельным полем в килограммах — для него масса действительно нужна.

## Что требуется сделать

1. Переписать `GameData.cs` под новый формат (GM, элементы орбиты, `parent`, `id`).
2. Написать `Assets/StreamingAssets/systems/saturn.json` по данным выше.
3. `GameMono.LoadGame` читает и разбирает файл вместо конструирования мира в коде.
4. `SimMono.CreateSim` строит тела обходом иерархии от корня, создавая каждое по элементам
   орбиты: элементы → `AstroDynamic.CalcRelativePositionAndVelocityAtEpoch` на `startEpoch`
   → относительные позиция и скорость → установка родителя и `SimTransform`.
5. Убрать `mass` отовсюду, кроме корабля; `SOI` считать через отношение GM.
6. Проверить масштаб отображения: `Constants.simDistanceMultiplier = 1e9` означает, что
   орбита Титана — 1.22 единицы Unity, а Феба — 12.9. Радиус Титана при этом 0.0026 единицы.
   Скорее всего множитель придётся уменьшить; подобрать так, чтобы система была видна
   целиком и луны при этом различались. Это временная мера, полноценное решение —
   отдельная задача про два режима отображения.

## Тесты

Данные — такой же код, и ошибка в одной цифре здесь стоит дороже, чем ошибка в формуле:
она не падает, а тихо делает мир неправильным.

1. **Файл читается**, все девять спутников и Сатурн загружены, у каждого непустой `id`,
   `id` уникальны.
2. **Иерархия корректна:** ровно один корень, у каждого нерутового тела существует родитель,
   циклов нет.
3. **Периоды совпадают со справочными.** Посчитанный из `a` и GM Сатурна период каждой луны
   совпадает с реальным с точностью 1 %: Мимас 0.942 сут, Энцелад 1.370, Тефия 1.888,
   Диона 2.737, Рея 4.518, Титан 15.945, Гиперион 21.28, Япет 79.33, Феба 550.3 (ретроградно).
   Это самая ценная проверка: она ловит и опечатку в `a`, и опечатку в GM, и путаницу
   километров с метрами.

   Таблица выше уже проверена на этих данных: максимальное отклонение — 0.55 % у Мимаса
   (его `a` в источнике округлено до 186 000 км), у остальных лучше 0.35 %, у Титана 0.02 %.
   Допуск 1 % выбран с запасом именно под Мимас; если тест падает больше чем на процент,
   дело в данных, а не в допуске.
4. **Сферы влияния разумны.** У каждой луны SOI меньше её большой полуоси и больше её
   физического радиуса. Для Титана SOI должен получиться около 43 тыс. км.
5. **Сферы влияния не пересекаются:** для любых двух соседних по орбите лун сумма их SOI
   меньше разности больших полуосей. Если проверка падает — данные противоречивы, и
   переходы между сферами влияния будут вести себя непредсказуемо.

   На данных выше условие выполняется везде с большим запасом; самая тесная пара —
   Титан и Гиперион: зазор 260 тыс. км против суммы SOI 44 тыс. км.
6. **Корабль внутри SOI своего родителя** и выше поверхности тела: `radius < r < SOI`.
7. **Эксцентриситет и наклонение в допустимых пределах:** `0 ≤ e < 1` для всех тел,
   `0 ≤ i ≤ 180`.
8. **Загрузка идемпотентна:** две повторные загрузки одного файла дают идентичное состояние.
9. **Битые данные дают внятную ошибку,** а не `NullReferenceException`: отсутствующий
   родитель, цикл, два корня, отрицательный GM, `e ≥ 1` у луны.

## Критерий приёмки

- Все существующие тесты остаются зелёными.
- Сцена `SystemBuilder` запускается, видны Сатурн и девять лун, они движутся по своим
  орбитам, периоды на глаз соответствуют реальным (Титан обходит Сатурн примерно за
  16 игровых суток при перемотке).
- Ни одной цифры физических данных не осталось в файлах `.cs`.
- Корабль стартует на орбите Титана и остаётся на ней.

## Отдельно, НЕ входит в эту задачу

1. **Два режима отображения (карта и локальный вид).** Корабль длиной сто метров при
   масштабе, где видна орбита Япета, имеет размер около 10⁻⁸ единицы Unity — его нельзя
   нарисовать в той же сцене. Это структурная развилка и отдельная задача.
2. **Кольца Сатурна** — не тело и не орбита, нужна своя модель.
3. **Точная привязка к плоскостям Лапласа** для Япета и Фебы.
4. **Сплюснутость Сатурна (J2)** — реально заметно возмущает орбиты близких лун, но в
   модели двух тел не учитывается вовсе. Осознанное упрощение.
5. **Солнце как источник тепла и света** — поле в формате данных заложить, механику не делать.

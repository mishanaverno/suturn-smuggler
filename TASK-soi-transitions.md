# Задача: актуальная скорость тел и переход между сферами влияния в рантайме

Репозиторий: `github.com/mishanaverno/suturn-smuggler`
Базовая ветка: `main`, поверх коммита `59879fe` (исправления математики `AstroDynamic`)
Unity 6000.2.0f1, тесты — Unity Test Framework (NUnit), сборка `Assets/Tests/Game.Tests.asmdef`

## Контекст

Космический симулятор с реалистичной астродинамикой. Движение аналитическое, по кеплеровым
орбитам, модель — патчед-коники: каждое тело движется вокруг ровно одного центрального тела,
взаимное притяжение не учитывается. Математика двух тел (`AstroDynamic`) исправлена и покрыта
инвариантными тестами — её трогать не нужно.

Задача состоит из двух частей. Часть A — предпосылка для части B, делать в этом порядке.

Ключевые типы:

- `Assets/Scripts/Space/Sim/SpaceObject.cs` — тело симуляции (планета, луна, корабль);
- `Assets/Scripts/Space/Sim/SimTransform.cs` — хранит `GLOBAL_R` / `GLOBAL_V`, отдаёт
  `RELATIVE_*` и `LOCAL_*`, обновляет Unity Transform;
- `Assets/Scripts/Space/Sim/SimMono.cs` — строит систему, держит списки `star`, `bodies`, `playerShip`;
- `Assets/Scripts/Game/GameMono.cs` — единственный источник времени, `GameMono.instance.Epoch` (секунды, double);
- `Assets/Scripts/Space/Sim/CoordianteSystem.cs` — переводы GLOBAL / RELATIVE / LOCAL (LVLH).

Соглашения, которые менять НЕЛЬЗЯ: всё в СИ; углы в `OrbitElements` в градусах, кроме
`meanAnomalyAtEpoch` (радианы); правая система координат, Z — полярная ось; публичные
сигнатуры `AstroDynamic` остаются как есть.

# Часть A. Скорость тела должна обновляться вместе с позицией

## Проблема

`SpaceObject.FixedUpdate`:

```csharp
public virtual void FixedUpdate() {
    if (!IsStar)
    {
        (Vector3d ECI_POS, _) = AstroDynamic.CalcRelativePositionAndVelocityAtEpoch(orbitParams, GameMono.instance.Epoch);
        if (ECI_POS != Vector3d.zero)
        {
            simTransform.SetRELATIVE_R(ECI_POS);
        }
    }
}
```

Скорость, которую `AstroDynamic` уже посчитал, выбрасывается в `_`. `GLOBAL_V` остаётся
тем значением, которое было передано в конструктор `SimTransform`, то есть скоростью на
момент запуска сцены — навсегда.

Следствия: `RELATIVE_V` и `LOCAL_V` у любого движущегося тела врут; относительная скорость
до другого тела, ориентация корабля по вектору скорости, стыковка и любая логика,
считающая от текущей скорости, работают с данными на t = 0. Сейчас это не проявляется
только потому, что `Maneuver` и `Ship.FixedUpdate` вызывают
`AstroDynamic.CalcRelativePositionAndVelocityAtEpoch` сами и берут скорость оттуда.

## Что сделать

1. Использовать оба выхода и записывать скорость:

```csharp
public virtual void FixedUpdate() {
    if (IsStar) return;
    var (relPos, relVel) = AstroDynamic.CalcRelativePositionAndVelocityAtEpoch(orbitParams, GameMono.instance.Epoch);
    simTransform.SetRELATIVE_R(relPos);
    simTransform.SetRELATIVE_V(relVel);
}
```

2. Убрать проверку `if (ECI_POS != Vector3d.zero)`. Это остаток от старого кода, где
   нулевой вектор означал «посчитать не смогли». Сейчас `AstroDynamic` при некорректных
   данных бросает исключение, а нулевой вектор — легальное значение. Проверка молча
   замораживает тело вместо того, чтобы показать ошибку.

3. **Порядок обновления.** `SetRELATIVE_R` и `SetRELATIVE_V` переводят относительные
   величины в глобальные через **текущее** `GLOBAL_R` / `GLOBAL_V` родителя. Значит
   родитель обязан обновиться раньше ребёнка в том же тике, иначе ребёнок на кадр
   отстаёт от родителя, и на быстрой перемотке времени (`TimeToggler` даёт до 66000×)
   это уже заметное расхождение.

   Сейчас `SimMono.bodies` заполняется в порядке убывания массы — это не то же самое,
   что «родитель раньше ребёнка». Нужно обновлять тела в порядке глубины иерархии:
   сначала звезда, затем её прямые дети, затем их дети. Порядок считать один раз при
   построении системы и пересчитывать при смене родителя (часть B), а не искать каждый кадр.

4. **Один источник истины для скорости.** Сейчас скорость лежит в двух местах:
   поле `SpaceObject.velocity` и `SimTransform.GLOBAL_V`. Первое после старта не
   обновляется никогда и используется только в логах. Оставить `SimTransform` как
   единственное хранилище, а `SpaceObject.velocity` либо удалить, либо превратить в
   свойство-обёртку над `simTransform.RELATIVE_V`.

5. `Assets/Scripts/Space/Sim/SimVelocity.cs` — незаконченная заготовка, нигде не
   используется. Либо задействовать её как контейнер трёх представлений скорости,
   либо удалить файл. Не оставлять как есть.

## Тесты части A

- После N шагов времени `simTransform.RELATIVE_V` совпадает со скоростью, которую
  даёт `AstroDynamic.CalcRelativePositionAndVelocityAtEpoch` на тот же момент.
- Численная производная позиции по времени сходится к записанной скорости:
  `(r(t+dt) − r(t−dt)) / (2·dt)` при малом `dt` совпадает с `v(t)` с относительной
  точностью не хуже `1e-6`. Это ловит и рассинхрон единиц, и перепутанные системы отсчёта.
- Для тела на двухуровневой иерархии (луна вокруг планеты вокруг звезды) абсолютная
  скорость равна сумме относительных скоростей по цепочке родителей.

# Часть B. Переход между сферами влияния в рантайме

## Проблема

Центральное тело назначается один раз, при построении системы, в `SimMono.CreateSim`:
перебором уже созданных тел проверяется `Vector3d.Distance(...) < body.SOI`. Дальше
`centralBody` не меняется никогда.

Это означает, что корабль, улетевший от Титана, продолжает считаться движущимся вокруг
Титана на любом расстоянии, а войдя в окрестности Реи, никак этого не замечает. Перелёт
между лунами — основная механика игры — сейчас невозможен в принципе.

## Что сделать

### B1. Решение о смене родителя — отдельная чистая функция

Логику выбора центрального тела вынести из `MonoBehaviour` в статический метод, который
не обращается ни к `GameMono.instance`, ни к `UnityEngine`. Время и состояние передавать
параметрами. Причина простая: иначе это невозможно протестировать без запуска сцены,
а именно здесь ошибки дороже всего — они проявляются раз в несколько минут полёта.

Примерная форма (имена на усмотрение):

```csharp
public static SpaceObject ResolveCentralBody(SpaceObject obj, SpaceObject currentCentral, IReadOnlyList<SpaceObject> allBodies, double hysteresis);
```

Правила:

- **Спуск.** Среди тел, у которых родитель — текущее центральное тело, если расстояние
  от объекта до кандидата меньше `SOI` кандидата, объект переходит к кандидату.
  Если подходит несколько (такого быть не должно, но проверять надо), брать ближайшее
  по отношению `расстояние / SOI`.
- **Подъём.** Если расстояние до текущего центрального тела больше его `SOI`, объект
  переходит к родителю текущего центрального тела.
- Спуск и подъём проверять до тех пор, пока состояние не перестанет меняться (объект
  может за один тик на большой перемотке пересечь сразу несколько границ), но с жёстким
  ограничением на число итераций, чтобы не зациклиться.
- Звезда (`IsStar`) — корень, выше неё подниматься некуда, её `SOI` бесконечен.

### B2. Гистерезис

Без него объект, идущий ровно по границе SOI, будет менять родителя каждый кадр, а вместе
с этим каждый кадр пересчитывать элементы орбиты с новой эпохой — это накопление ошибки
и дёргающаяся орбита на экране.

Порог входа и порог выхода должны различаться: входить при `d < SOI`, выходить при
`d > SOI · (1 + eps)`, где `eps` порядка `0.01`. Значение вынести в константу с комментарием.

### B3. Сам переход обязан сохранять абсолютное состояние

Это главный инвариант всей части. При смене родителя:

1. запомнить абсолютные `GLOBAL_R` и `GLOBAL_V` объекта **до** смены;
2. установить нового родителя (`centralBody` и `simTransform.RelativeTo`);
3. записать относительные позицию и скорость как разность с абсолютным состоянием
   нового родителя;
4. пересчитать `orbitParams` через `AstroDynamic.CalculateOrbitElements` с `mu` нового
   родителя и `epoch = GameMono.instance.Epoch` — **обязательно текущей эпохой**, не нулём
   и не эпохой старой орбиты;
5. пересчитать `SOI` объекта;
6. обновить порядок обновления тел из пункта A3.

Физически объект не должен ни на метр сдвинуться и ни на метр в секунду изменить скорость.
Меняется только система отсчёта, в которой описывается его движение.

Шаг 3 требует **корректной абсолютной скорости родителя** — отсюда зависимость от части A.

### B4. Кто именно переходит

Проверять переходы каждый `FixedUpdate` для всех тел дорого и бессмысленно: луны своих
SOI не покидают. Ввести признак (флаг на `SpaceObject` или проверку типа), по которому
переходы считаются только для корабля и других подвижных объектов. Планеты и луны
остаются на своих родителях.

### B5. Отрисовка

`OrbitRenderer` и `SOIRenderer` берут центральное тело у объекта. Убедиться, что при смене
родителя линия орбиты перестраивается вокруг нового центра в том же кадре, а не остаётся
висеть вокруг старого. Если они кешируют центр — сбрасывать кеш при переходе.

## Тесты части B

Тесты на чистую функцию из B1 и на инвариант из B3 — обязательны. Тесты, требующие
запуска сцены, писать не нужно.

1. **Сохранение абсолютного состояния.** После смены родителя абсолютные позиция и
   скорость совпадают с теми, что были до смены, с относительной точностью `1e-12`.
2. **Непрерывность траектории.** Объект на гиперболической траектории отхода от луны:
   на каждом шаге времени сравнивать абсолютную позицию с позицией на предыдущем шаге;
   в момент перехода скачка быть не должно — смещение за шаг остаётся того же порядка,
   что и на соседних шагах.
3. **Отсутствие дребезга.** Объект, помещённый ровно на радиус SOI и удерживаемый там,
   за 1000 тиков меняет родителя не более одного раза.
4. **Спуск.** Объект, входящий в SOI луны, получает луну центральным телом; орбита вокруг
   луны при этом замкнута, если относительная скорость меньше второй космической, и
   разомкнута, если больше.
5. **Подъём.** Объект, разогнанный выше второй космической относительно луны, покидает её
   SOI и получает планету центральным телом.
6. **Многоуровневый переход за один тик.** При очень большом шаге времени объект,
   пересёкший сразу две границы, оказывается в правильной сфере влияния, а не застревает
   на промежуточном уровне.
7. **Детерминизм.** Одна и та же последовательность шагов даёт одну и ту же цепочку
   родителей.

## Критерий приёмки

- Все существующие тесты остаются зелёными.
- Корабль в сцене `SystemBuilder` может прожечь двигатель, уйти из сферы влияния одного
  тела и продолжить полёт вокруг другого без скачка позиции, скорости и без перестроения
  всей системы.
- Линия орбиты и сфера влияния перерисовываются вокруг нового центра сразу.
- На перемотке 66000× тела не расходятся друг с другом и не дёргаются на границах SOI.

## Отдельно, НЕ входит в эту задачу

Перечислено, чтобы не расширять область работ:

1. **Предсказание момента входа в чужую SOI** — чтобы игрок мог целиться в перелёт, нужна
   не только реакция на пересечение границы, но и прогноз: когда траектория пересечёт SOI
   цели. Это отдельная и существенно более сложная задача (поиск корня по времени вдоль
   двух кеплеровых орбит).
2. **Реальные данные системы Сатурна.** `GameMono.LoadGame` до сих пор собирает
   захардкоженные Солнце, Землю и Луну прямо в C#. Нужны Сатурн с лунами, реальные массы
   и элементы, загрузка из файла данных.
3. **Floating origin.** `SimTransform.UpdateReprezentation` делит на
   `Constants.simDistanceMultiplier` и приводит к `float`. Пока камера смотрит на систему
   целиком, точности хватает; при работе вблизи корабля на расстоянии миллиарда метров
   от начала координат — перестанет.
4. **Конечная тяга вместо импульса.** `Ship.FixedUpdate` уже применяет тягу, но накопленный
   `dv` прикладывается как мгновенный импульс раз в секунду. Для длинных прожигов это
   неверно и требует отдельного решения.
